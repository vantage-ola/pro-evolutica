# PES 2013 asset research

## Verified AFS containers

All 19 `.img` files in the inspected local PES 2013 `img/` directory begin with
`AFS\0`. Their little-endian entry counts and offset/size pairs pass the bounds
checks in `tools/afs_inspect.py`: 55,593 slots in total, including 1,273 empty
slots. Full per-container hashes and indices remain in ignored
`private/reports/`. These results describe this copy, not every PES 2013 edition.

The basic layout agrees with the
[cri-afs format description](https://github.com/soyjxck/cri-afs#format): four magic
bytes, a 32-bit count, then pairs of 32-bit offsets and sizes. The older
[PES6 AFS reader](https://github.com/lazanet/PES6-AFS-Tools/blob/master/AFS.java)
also reads this flat table and warns against treating Konami's extra metadata as
ordinary filenames. It does not establish PES 2013 payload compatibility.
The new reader uses the observed layout and Python's standard library; no source
code or dependencies were imported from either project.

## Verified WESYS decoding

`tools/wesys_unpack.py` decoded all ten non-empty `dt10.img` entries, producing
140,960 bytes in total. For each entry, the little-endian lengths at offsets 8
and 12 describe the compressed zlib stream and its decoded size. Zero padding
after that stream ranges from 2 to 10 bytes in this sample.

The 16-byte header layout agrees with
[Sider's WESYS documentation](https://github.com/pes-modding/sider7/blob/master/doc/scripting.html):
three header bytes, five `WESYS` bytes, then compressed and uncompressed lengths.
Little-endian interpretation is verified against the actual PES 2013 entries;
support is limited to the observed `00 01 01` variant. No third-party reader was
installed or copied.

For entry 1:

- Compressed stream: 1,821 bytes, followed by three zero padding bytes.
- Decoded output: 28,272 bytes.
- Decoded SHA-256:
  `2cf527971ca3b7222c69dd0d3681e56a79fbe319763f8070288274fcb42e5e56`.
- A separate one-shot `zlib.decompress()` of the declared compressed range
  matched the tool output byte-for-byte. This comparison uses the same underlying
  zlib library; it verifies wrapper handling, not a second compression algorithm.
  `shasum -a 256` independently agreed with the output hash.

All ten streams reach zlib's end marker, pass its checksum, consume exactly the
declared compressed range and produce exactly the declared decoded length.
Raw entries, decoded content and full reports remain in ignored `private/`.
This does not establish support for every WESYS entry in the other 18 archives.

## Decoded content: likely compiled scripts

All ten decoded entries contain `FA FA 52 49 51 53` at offset 32. These bytes
match Squirrel's `0xFAFA` bytecode tag and little-endian `SQIR` closure marker,
defined in its [public header](https://github.com/albertodemichelis/squirrel/blob/master/include/squirrel.h)
and [object definitions](https://github.com/albertodemichelis/squirrel/blob/master/squirrel/sqobject.h).
Embedded strings include `.nut` source names under a `sim/squirrel` directory.

Together these observations support the classification **likely Squirrel compiled
scripts**. The exact VM version, the outer 32-byte structure and the bytecode
instructions have not been parsed or validated. No script was executed and no
game behaviour was recreated. These entries are not yet a rendering sample.

  Other wrapper fields remain uninterpreted.
- DDS begins at decoded-file offset 48: **256 × 256, DXT1, nine mip levels**.
  The calculated mip sizes plus the 128-byte header equal 43,832 exactly.
- DDS SHA-256:
  `24907cb3f60faefa8993266b6d09448f7d0df5efc48eab0d5d04f1597e458912`.
- PNG preview: 17,631 bytes; SHA-256
  `f240ea4fb1487dbbc6f64865b77708aea5708e35096565cc53a1d37579a482bb`.

`tools/pes_texture.py` checks the inferred bundle/WE00 bounds and the standard
[DDS header](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-header).
Its original DXT1 preview decoder follows the documented
[colour/alpha block layout](https://learn.microsoft.com/en-us/windows/win32/direct3d9/opaque-and-1-bit-alpha-textures).
No code from the GPL model tools was integrated. Support is restricted to the

The DDS output exactly matches the 43,832-byte source range at offset 48.
An independent `shasum` agrees with its checksum. macOS `sips` successfully
converted the extracted DDS to PNG. After PNG filter decoding, its RGBA output
matches alpha exactly and differs in RGB by at most one out of 255. Of 262,144
channels, 15,547 differ; the previews are not pixel-identical. Visual inspection
shows a readable grayscale atlas. Its exact in-game use remains unknown.

Original DDS, both previews and full verification reports remain in ignored
`private/`. The asset must be supplied locally; source/test fixtures contain no
commercial texture data.

## Static ball geometry and textures

The selected entry 17 was decoded with the independent
[KTMDL reader at commit 0a0284f](https://github.com/moth1995/pes2008-2013-tools/blob/0a0284fc9127beca45397ba7009883af2f2be6fd/pes_ktmdl_importer/ktmdl.py).
Its GPL-3.0-or-later source was saved under ignored research storage, read in
full, and run with `parse_bytes()` on the local model. It uses the standard
library; no package was installed and no reference source was incorporated into
our code or APK. The 33,483-byte reference source has SHA-256
`6dc2e924e9df136d72476343a0fd27feccac099fcdeb317ec9bcc49522d8ca63`.

Our static decoder agrees exactly with that reader on all 682 positions,
normals, tangents, binormals, UV0 and UV1 values, all 1,748 indices and the
ordered list of 1,144 triangles. Repeated-index strip windows still advance
parity; restart markers reset it. The sample has 602 repeated-index windows and
no restarts. Every retained triangle has positive area and a cross product
aligned with its summed vertex normals: 1,144 aligned, zero opposed, zero
perpendicular. Areas range from approximately `1.4800023e-5` to `1.6404193e-4`
in squared source units. Normal lengths range from 0.99999916 to 1.00000072.

The one root bone has parent -1 and two exact identity matrices. Its packet's
bone palette contains only bone 0; there are no blend-weight/index attributes,
morphs or extra records. We preserve local XYZ without applying a guessed
transform or unit conversion. The bounds are approximately ±0.11 on all axes.
A symmetric ball cannot establish the game's world-up axis or physical unit
scale. The packet's three-value bound centre is zero.

`tools/ktmdl_export.py` produces an OBJ with positions, UV0, normals and faces.
The 114,904-byte local output has SHA-256
`25b7d305933715660de00d0822e15e6c58c71859d4e3166e0eec1d7a63f68e4f`.
Parsing its decimal values back to float32 reproduces every exported value's
bytes, and its one-based face indices reproduce the reference triangle list.
UV0 stays in the source convention: U 0.002203–0.997636, V 0.022924–0.987670.
OBJ contains no texture, MTL, tangent data or proprietary shader implementation.

## One evaluated pose

`tools/anm_pose.py` now evaluates an integer dense sample and writes a local
geometry-only OBJ. The 41 original tests check XYZW rotation packing, omitted
components/signs, rotations about translated joints, absolute local rotations,
parent/root propagation, palette mapping, both residual orders and bind recovery.
Rigid matrices and complete dense rotation tracks are required; morphs, unknown
packed flags, invalid samples and existing outputs are refused.

The source-based transform convention is:

- A is the global rest matrix and B its inverse, in file row-vector notation.
- Local rest is A × parent B. Clip rotations replace local rest rotations.
  Missing translation tracks keep the local rest translation.
- Animated global is local × parent global; vertex skin matrices are
  B × animated global. Positions are blended through the packet palette.
- Source axes and units are retained, with no coordinate conversion.

This agrees with the pinned
[animation importer’s local/global construction](https://github.com/moth1995/pes2008-2013-tools/blob/0a0284fc9127beca45397ba7009883af2f2be6fd/pes_anm_importer/__init__.py)
after translating its column-vector notation. That source is 25,328 bytes,
SHA-256 `f9c369ab775384c5d4832f55c786660ccfc6d7891ffc0badd5c6d340000b6d6e`.
It was read privately; Blender and its add-on were not installed or run.
No third-party implementation was incorporated into the repository.

Packed rotations use low bits 0–1 for the omitted XYZW component. Three 15-bit
values occupy bits 32–46, 17–31 and 2–16 in that component order, skipping the
omitted component. Each is `(value − 16383.5) / 23169.767578125`; the omitted
component is the positive square root completing unit length. Bit 47 is zero
in all selected samples; the evaluator refuses a set bit. All 1,729 decoded
rotations match the pinned reader exactly.

Sample 45 is 1.5 seconds into the selected 30 FPS clip. A separate private
calculation uses the reference readers' decoded values, quaternion composition
and vector rotation, rather than the evaluator's matrix operations. It computes
rest translations using the exact inverse of parent A. All 6,736 vertex positions
and 19 joint origins agree within `1.056815e-6` source units for both weight orders.
Triangle lists agree exactly. The small difference is consistent with the file's
rounded stored inverse matrices; this is not a runtime Blender comparison.

Residual-first produces a coherent raised-arm pose in a private CPU diagnostic.
Residual-last produces visibly stretched arms and torso. Among 1,837 exact source
position duplicate groups, maximum posed separation is 0.011466 with first and
0.712780 with last; 141 versus 238 groups exceed 1e-5. Duplicates can belong to
separate surfaces, so this measures consistency rather than proving all seams
must coincide. Together, the numeric and visual evidence supports **first for
this pair**. The CLI still requires the weight order explicitly.

Bind recovery has maximum vertex distance `1.442926e-6` with first and
`2.047639e-6` with last. Both reproduce rest geometry within the supported rigid
matrix tolerance; bind recovery alone cannot choose a weight order. The model's
extra count is 1, referring to a 32-byte record at offset 192 in the reference;
its meaning is uninterpreted and is not used to deform geometry.

Full reference values, both posed OBJs, hashes, the independent calculation and
the CPU diagnostic remain under ignored `private/research/pose/`. The diagnostic
shows rest, first and last from left to right; it uses flat shading without game
materials. See [the commands and results](../verification/tools.md#pose-evaluation).
No game pose or action identity has been confirmed. Check sequence continuity
before native deformation and Android playback.
