# PES 2013 asset research

## Verified AFS containers

All 19 `.img` files in the inspected local PES 2013 `img/` directory begin with
`AFS\0`. Their little-endian entry counts and offset/size pairs pass the bounds
checks in `tools/afs_inspect.py`: 55,593 slots in total, including 1,273 empty
slots. Full per-container hashes and indices remain in ignored
`private/reports/`. These results describe this copy, not every PES 2013 edition.

The basic layout agrees with the
[cri-afs format description](https://github.com/soyjxck/cri-afs#format): four magic
bytes, a 32-bit count, then pairs of 32-bit offsets and sizes. The older
[PES6 AFS reader](https://github.com/lazanet/PES6-AFS-Tools/blob/master/AFS.java)
also reads this flat table and warns against treating Konami's extra metadata as
ordinary filenames. It does not establish PES 2013 payload compatibility.
The new reader uses the observed layout and Python's standard library; no source
code or dependencies were imported from either project.

## Smallest real sample

`dt10.img` is 26,624 bytes, with 11 slots and one empty slot.

- Archive SHA-256:
  `64e652d268d00d35b6f4b5db3ec0442b279ca1395e234a480ab6db12bd6860f4`.
- Extracted slot: index 1, offset 2,048, size 1,840 bytes.
- Extracted SHA-256:
  `227dbf38d63e78cb03e64bdef8123e73e59ec53029a3fcd7697ea3ed13bc136f`.
- Independent source read: seek to offset 2,048, read 1,840 bytes, compare with
  the extraction. Bytes and SHA-256 match.
- All ten non-empty entries begin with `00 01 01 57 45 53 59 53`, containing the
  ASCII bytes `WESYS`. Their compression is now verified below.

The tool extracts raw entry bytes without executing, modifying or decoding them.
No sample payload or game archive is checked into Git. See
[tool usage](../TOOLS.md#inspect-an-afs-container-and-extract-one-entry).

## Verified WESYS decoding

`tools/wesys_unpack.py` decoded all ten non-empty `dt10.img` entries, producing
140,960 bytes in total. For each entry, the little-endian lengths at offsets 8
and 12 describe the compressed zlib stream and its decoded size. Zero padding
after that stream ranges from 2 to 10 bytes in this sample.

The 16-byte header layout agrees with
[Sider's WESYS documentation](https://github.com/pes-modding/sider7/blob/master/doc/scripting.html):
three header bytes, five `WESYS` bytes, then compressed and uncompressed lengths.
Little-endian interpretation is verified against the actual PES 2013 entries;
support is limited to the observed `00 01 01` variant. No third-party reader was
installed or copied.

For entry 1:

- Compressed stream: 1,821 bytes, followed by three zero padding bytes.
- Decoded output: 28,272 bytes.
- Decoded SHA-256:
  `2cf527971ca3b7222c69dd0d3681e56a79fbe319763f8070288274fcb42e5e56`.
- A separate one-shot `zlib.decompress()` of the declared compressed range
  matched the tool output byte-for-byte. This comparison uses the same underlying
  zlib library; it verifies wrapper handling, not a second compression algorithm.
  `shasum -a 256` independently agreed with the output hash.

All ten streams reach zlib's end marker, pass its checksum, consume exactly the
declared compressed range and produce exactly the declared decoded length.
Raw entries, decoded content and full reports remain in ignored `private/`.
This does not establish support for every WESYS entry in the other 18 archives.

## Decoded content: likely compiled scripts

All ten decoded entries contain `FA FA 52 49 51 53` at offset 32. These bytes
match Squirrel's `0xFAFA` bytecode tag and little-endian `SQIR` closure marker,
defined in its [public header](https://github.com/albertodemichelis/squirrel/blob/master/include/squirrel.h)
and [object definitions](https://github.com/albertodemichelis/squirrel/blob/master/squirrel/sqobject.h).
Embedded strings include `.nut` source names under a `sim/squirrel` directory.

Together these observations support the classification **likely Squirrel compiled
scripts**. The exact VM version, the outer 32-byte structure and the bytecode
instructions have not been parsed or validated. No script was executed and no
game behaviour was recreated. These entries are not yet a rendering sample.

## Verified texture: dt08.img entry 2

The tested path is AFS entry 2 → WESYS decode → bundle index 0 → WE00 → DDS.

- Raw entry: 16,656 bytes; SHA-256
  `783822df3a5a1e32cfb6da62d4e951dc6808ea3c4697703640d47255a8dcd6da`.
- Decoded bundle: 43,888 bytes; SHA-256
  `964a241ef554df7213ce5c3d7ee34c46a86847dfaf90a3cbcec4458b1d436c92`.
- Bundle count: one; table offset: 8. The observed 12-byte record gives chunk
  offset 32, size 43,848 and an uninterpreted value `0xfffffff0`.
- The WE00 wrapper is 16 bytes. Its field at offset 8 gives DDS length 43,832.
  Other wrapper fields remain uninterpreted.
- DDS begins at decoded-file offset 48: **256 × 256, DXT1, nine mip levels**.
  The calculated mip sizes plus the 128-byte header equal 43,832 exactly.
- DDS SHA-256:
  `24907cb3f60faefa8993266b6d09448f7d0df5efc48eab0d5d04f1597e458912`.
- PNG preview: 17,631 bytes; SHA-256
  `f240ea4fb1487dbbc6f64865b77708aea5708e35096565cc53a1d37579a482bb`.

`tools/pes_texture.py` checks the inferred bundle/WE00 bounds and the standard
[DDS header](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-header).
Its original DXT1 preview decoder follows the documented
[colour/alpha block layout](https://learn.microsoft.com/en-us/windows/win32/direct3d9/opaque-and-1-bit-alpha-textures).
No code from the GPL model tools was integrated. Support is restricted to the
tested layout and flat DXT1 textures; it is not a general PES asset parser.

The DDS output exactly matches the 43,832-byte source range at offset 48.
An independent `shasum` agrees with its checksum. macOS `sips` successfully
converted the extracted DDS to PNG. After PNG filter decoding, its RGBA output
matches alpha exactly and differs in RGB by at most one out of 255. Of 262,144
channels, 15,547 differ; the previews are not pixel-identical. Visual inspection
shows a readable grayscale atlas. Its exact in-game use remains unknown.

Original DDS, both previews and full verification reports remain in ignored
`private/`. The asset must be supplied locally; source/test fixtures contain no
commercial texture data.

## Selected KTMDL model samples

The [standalone KTMDL research reader](https://github.com/moth1995/pes2008-2013-tools/blob/main/pes_ktmdl_importer/ktmdl.py)
identifies an eight-byte `KTMDL` signature, a 192-byte header, geometry tables,
relative stream references and vertex declarations. Its source is marked
GPL-3.0-or-later. No code was installed or incorporated; those layout observations
were checked against the local samples before writing the limited inspector.

A bounded exploratory search planned up to 300 small compressed WESYS entries
per selected archive and stopped after three signatures. It found them in the
first three entries checked in `dt0b.img`: indices 35, 1 and 17. This is a partial
search, not a model inventory. Supported WESYS decoding consumed exactly the
compressed streams and produced 761,552 bytes total with no decode failures.

The archive SHA-256 from the earlier inventory is
`e77dddd5fb9df4362bf71ec16530ed6af4af748f9a9eba1ee73b71e1ebd13ad1`.
The search checked the actual AFS header/table against the saved entry records.
Two samples were selected for further work:

### Small format fixture: entry 35

- AFS offset 10,680,320; raw entry 620 bytes. SHA-256:
  `d5b68e489f77310159576cfdc4d3f2fb85bbf30e748807d7e343683d7da9d513`.
- Decoded bundle 6,288 bytes, two entries with table offset 8.
- Model at bundle offset 32, size 1,120 bytes. Its declared size agrees exactly.
  Standalone model SHA-256:
  `d7d9c24e9b590a07f5f4b793bdd9fa04f6ecb04d8e4f7491cf1ac06f6c91cac4`.
- Little-endian version 2.1; one packet, four vertices, four 16-bit indices.
  Position/normal/UV declarations occupy a 32-byte vertex stride.
- All positions are finite, all indices are in range, and the strip has two
  triangle windows without repeated indices. Bounds span approximately
  -0.3 to 0.3 in X/Z, with constant Y around 0.02: this is a flat sample.
- The other bundle entry starts with WE00, but the existing texture reader's
  length interpretation exceeds its range. That layout is unsupported; this
  does not establish that the source file is damaged.

### Spatial model candidate: entry 17

- AFS offset 5,992,448; raw entry 81,872 bytes. SHA-256:
  `22cb98c9b9fc6f8a56f6d626d45bf15ddf11a0ba1a3f6e92c120ac3c1ad311b9`.
- Decoded bundle 748,000 bytes, four entries with table offset 8.
- Model at bundle offset 64, size 48,384 bytes, exactly matching its declared size.
  Standalone model SHA-256:
  `c93c7430f5534093fef4499dd5c7d3e4be5b530613558ac683d3bf6122e22aa3`.
- Little-endian version 2.2; one packet, 682 vertices, 1,748 16-bit indices.
  Six declared elements use a 64-byte stride.
- All positions are finite and indices are in range. Bounds extend approximately
  -0.11 to 0.11 on each axis. The strip contains 1,144 triangle windows without
  repeated indices and 602 windows with repeated indices; no restart markers.
  This does not yet validate triangle area, winding or the object's identity.
- Bundle indices 1 and 3 pass the existing 512 × 512 DXT1 DDS checks. Index 2
  uses an unsupported DDS format. Material references have not been resolved;
  sharing a bundle does not establish which texture belongs on the model.

Independent archive seek/read comparisons match both raw extractions. The
standalone models match their bundle ranges byte-for-byte, and `shasum -a 256`
agrees with their reported hashes. The inspector validates geometry table ranges,
relative stream/declaration references, finite positions and index bounds.
It does not validate bones, materials, UV values or animation.

Inputs, extracted models and full reports remain under ignored `private/`.
Tests use original generated geometry. An independent model reader or viewer
comparison remains pending before geometry export or Android rendering.
